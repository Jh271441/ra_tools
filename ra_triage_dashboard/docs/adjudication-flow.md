# 当前标注与裁决流程（2026-10-23）

本文以本次代码和实际生效规则为准，供讨论裁决规则使用；没有因为界面增加“待裁决”就改写业务优先级。数据库及 API 内部仍兼容原有枚举，页面统一使用业务名称。

## 先区分四类数据

| 数据 | 作用 | 裁决影响 |
|---|---|---|
| Case 期望输出 | 正确触发 / 误触发 / 无需协助的共享人工结论 | 参与任务内与 Issue 级裁决 |
| Issue Tags 与依据 | 场景、交互、脱困标签及每人的说明 | 原始意见保留；不以 Tags 是否相同决定三分类是否冲突 |
| Case 排除意见 | 该 Issue 是否应排除，独立于模型 Run | 使用有效任务裁决或各人当前排除意见 |
| Run 模型复核 | 对某次模型结果的评价、完成状态和评论 | 不作为 Case 最终分类或排除的覆盖优先级 |

GT 是独立的评测基准；人工裁决只改变共享人工结论。与 GT 不一致会显示需复核，更新 GT 仍需单独预览、确认。Trail 当前标记是另一份外部事实，本地保存和裁决不会自动写 Trail。

## 优先级速查

| 范围 | 实际优先级或合并规则 | 不会自动覆盖的内容 |
|---|---|---|
| 同一标注来源、同一作者 | 最新有效个人版本替代自己的旧版本；旧版仍可审计 | 不能替代他人的意见 |
| 同一任务标注来源 | 当前有效的显式任务裁决优先；否则按所需人员的当前意见求一致 | 任务裁决不能压过另一个来源 |
| Issue 三分类 | 当前有效 Issue 裁决优先；否则全部来源都要形成相同分类 | 不按作者职位、管理员身份、票数多数或跨来源时间先后选赢家 |
| Issue 排除 | 有效任务裁决先在本来源替换意见，再合并全部来源；任一 true 即排除 | Issue 三分类裁决不能取消排除；一个来源 false 不能取消其他来源 true |
| Issue Tags | 汇总有效任务裁决或个人当前版本的 Tags 并去重；原始个人标签/说明可查 | 不决定三分类是否冲突；Issue 三分类裁决不产生一套全局最终 Tags |
| 排除汇总使用的理由 | 先从有效排除版本中取版本 ID 最大的一份，再读该版本的理由或其精确迁移来源 | 不拼接所有人的说明；没有“最长理由优先”或“管理员理由优先” |
| Run 模型复核 | 仅解释本次模型结果及个人复核状态 | 不自动裁定 Issue 分类、排除或 GT |
| GT、Trail | 各自保留当前事实，通过独立受控流程更新 | 本地标注和裁决不自动覆盖它们 |

这里的“来源”是可追踪的一份 Case 标注记录，可能与任务或选样 Run 相关；不能把“最近一次打开的任务”当成最高优先级。联合复核保存共享 Case 标注和 Run 复核，并另记任务确认关系；来源栏的任务归属不等于又生成一份独立投票。联合复核任务内展示使用本人分配及被该任务确认的精确版本，其只读任务投影不能冒充可写的传统标注任务裁决。

联合复核的任务提交进度依赖同一分配下 `model_review_submitted` 和 `case_label_acknowledged` 两个标记；它与共享 Issue 是否已经达成一致是两种状态。因此“本人已提交”和“Issue 仍待裁决”可以同时成立。

## 1. 分类结论如何产生

```mermaid
flowchart TD
  A[每个标注来源：任务内或任务外] --> B[同一来源内，每人仅取最新有效提交\n旧版本和原意见保留]
  B --> C{该来源有显式任务裁决？}
  C -->|有效，来源版本仍一致| D[采用任务裁决的完整结果]
  C -->|已有裁决但来源版本变化| E[需重新裁决]
  C -->|没有| F{所需人员已提交\n且期望输出均有效？}
  F -->|否| G[该来源待完成]
  F -->|是| H{期望输出完全一致？}
  H -->|是| I[该来源形成结论]
  H -->|否| J[该来源待裁决\n不使用多数票]
  D --> K[汇总所有有效来源]
  E --> K
  G --> K
  I --> K
  J --> K
  K --> L{有绑定当前来源指纹的\n有效 Issue 级裁决？}
  L -->|是| M[采用 Issue 裁决的期望输出]
  L -->|已有，但指纹变化| N[需重新裁决]
  L -->|没有| O{来源都已形成相同结论？}
  O -->|是| P[共享分类结论]
  O -->|否| Q[过期 / 冲突 / 待完成\n保持未决]
  M --> R[与独立 GT 比较\n一致或需 GT 复核]
  P --> R
```

来源内部状态依次检查：裁决失效 → 人员或输出未齐 → 分类冲突 → 一致形成结论。跨来源则依次检查：过期 → 任一来源冲突或来源结论不一致 → 未完成 → 一致形成结论。历史导入中已确认的冲突也保留，不能被表面一致掩盖。

Issue 级裁决优先级最高，但创建时有边界：所有**任务来源**必须先形成有效结论；任务内未完成、冲突、过期时，必须先处理任务。任务外来源也参与 Issue 汇总，不能因为“自由标注”而自动忽略。任务外未决意见可以由显式 Issue 裁决统一处理。

同一来源的任务裁决只替代该来源，不能自动压过其他来源。不同来源之间不按更新时间选一条，也不按作者身份或管理员身份自动覆盖；普通保存永远是个人意见，只有显式裁决进入裁决优先级。

## 2. 排除如何生效

```mermaid
flowchart TD
  A[读取 Case 的当前排除证据] --> B{存在 Case 证据？}
  B -->|没有| C[按所选 Run 的旧 Review 排除记录兜底]
  B -->|有| D[每个来源分别处理]
  D --> E{有有效任务裁决？}
  E -->|有| F[仅采用该来源的裁决排除值]
  E -->|没有或已失效| G[采用该来源各人最新有效意见]
  F --> H[合并所有来源的有效排除意见]
  G --> H
  H --> I{排除与不排除意见并存？}
  I -->|是| J[显示排除待裁决\n裁决前仍按当前保守规则生效]
  I -->|否| K[无需排除分歧提示]
  J --> L{任一有效意见为排除？}
  K --> L
  L -->|是| M[本地汇总为排除]
  L -->|否| N[本地汇总为不排除\n阻断旧 Run 的排除兜底]
  M --> O[与 Trail 实际状态独立展示]
  N --> O
  C --> O
```

当前是“任一有效 true 则排除”，不是多数票。“待裁决”提示表明存在 true/false 分歧，未在后台自动替换已有意见。任务裁决为 false 只替代那份任务；若其他有效来源仍 true，Issue 本地汇总仍 true。

**现有结构限制：**Issue 级标签裁决只保存最终三分类，不保存排除决定；当前没有一个能覆盖所有来源的独立 Issue 排除裁决。页面“排除裁决”复用的是**完整任务裁决**：必须同时确认该任务的期望输出、Tags、证据缺口、理由和排除值。可以处理 pending 或同标签但排除意见不一致的任务。它不是仅改一个布尔值的全局裁决。

## 3. 实际操作顺序

1. 查看来源与原始意见，确认是分类分歧、排除分歧，还是只有理由缺失。
2. 需要普通补充时保存自己的意见，保留他人的当前意见。
3. 某个任务来源未完成或冲突：在该任务内完成标注或显式任务裁决。在 Issue 标签标题右侧的状态按钮中展开“调整裁决”，选择相应任务，统一处理分类与排除意见。
4. 各任务来源形成结论，但跨来源仍冲突：点击 Issue 标签标题右侧的状态按钮，在“调整裁决”中选择“Issue 最终分类”，填写分类与依据。
5. 提交绑定全部当前来源版本和此前裁决版本；并发变化返回冲突，须刷新来源后重新确认。
6. 后续任何相关来源版本变化，已有裁决需重新确认；历史版本和依据保留。
7. 如要把本地排除和理由发布到 Trail，另走“问题排除 → 选中 → 预览 → 明确确认 → 写入 → 读回”。空理由不会清空远端。

本地改成不排除不会撤销 Trail 中已存在的 true；目前受控 writer 只支持写 true 和理由更新，远端取消排除没有在本次增加。

## 4. 理由来源与状态

优先读取当前生效排除版本的非空 Case 理由。若当前生效的是迁移旧版本且理由空，只关联**它自己 source_annotation_id 对应**的原始排除备注；必须同 Issue、同作者、原记录也勾选排除，并能在迁移后的模型复核理由中逐字核验。不会拿其他作者、任意更旧的备注或 Trail 文本来假造人工提交。新的普通空提交也不会被旧备注覆盖。

这次关联是只读来源恢复：原作者、原时间、原 Review ID 和 Case revision ID 可查；不新增标注、不改变分配、任务进度、裁决来源指纹、GT 或 Trail。审计时45条候选：15条已有理由、18条符合精确来源恢复、12条当前对应原文和 Trail 均空。数字是时点事实，页面不硬编码。

| Trail 与理由事实 | 页面主状态 |
|---|---|
| 排除未生效或未设置 | 待排除 |
| 已排除；理由缺失或两端不一致 | 理由待更新 |
| 已排除；非空理由一致 | 已排除 |
| 查询未完成 / 失败 | 查询中 / 无法确认 |

“理由待更新”可能是本地待补充，也可能是已有非空新理由待提交；只有满足原有安全条件的非空新理由能进入写入集合。已同步保留为内部兼容枚举，页面不再作为主状态名称。

## 例子：当前规则会怎样处理

| 输入 | 当前结果 |
|---|---|
| 同一来源三人分别提交误触发、误触发、正确触发 | 分类待裁决；不会用两票盖过一票 |
| 来源 A 已裁定误触发；来源 B 已形成正确触发 | 跨来源冲突；A 的任务裁决没有全局优先权 |
| 所有任务来源已形成结论，但任务外个人意见相冲突 | 可查看全部来源并显式作 Issue 三分类裁决；不能自动忽略任务外意见 |
| 一人要求排除，另一人不排除，分类恰好一致 | 分类可一致；排除显示待裁决，当前本地排除仍为 true |
| 来源 A 裁定不排除，但来源 B 仍要求排除 | 本地仍排除；不存在全局 Issue 排除裁决来直接盖过 B |
| 来源发生新提交，即使只改理由或 Tags | 版本变化可能使依赖它的裁决过期；目前没有按业务字段拆分的裁决指纹 |
| 本地全部有效意见为不排除，但 Trail 当前为排除 | 本地不排除、Trail 仍排除；不会自动写远端撤销 |

## 5. 适合继续讨论的规则选择

- 排除应继续“任一 true 保守排除”，还是仅在一致/裁决后排除？分歧时是否保持上一次已确认结论？
- 是否增加独立 Issue 排除裁决，并决定它是否覆盖所有任务和任务外来源？
- 是否把任务标签裁决和排除裁决彻底分开，避免修改排除时一并确认分类与 Tags？
- 只改理由、Tags 等无关字段是否也应使分类/排除裁决过期，还是分别维护来源指纹？
- 标签分类一致但排除分歧时，分类完成和排除待裁决是否应分别影响任务完成数？
- 本地不排除但 Trail 仍排除时，谁有权发起远端撤销，如何预览和审计？

上述是待讨论问题，不是已实现的新规则。

## 当前界面入口（2026-10-23 更新）

Issue 标签标题右侧只有一个状态按钮，合并原状态、原因、Issue裁决及排除详情/裁决入口。弹窗沿用标注历史的单列卡片，默认展示当前结果形成流程、分类与排除原因、各人的原始意见和裁决记录。页面 Issue 标签标题同一行的 info 按钮可直接查看简明规则流程，无需先进入裁决弹窗。

“调整裁决”在同一弹窗内选择范围：Issue 最终分类，或服务端确认可写的具体任务。一个保存只调用对应范围的一个接口，保留原并发校验、角色限制、来源版本和裁决历史；不把任务裁决冒充全局Issue排除裁决。普通排除勾选与判错复核复用同一组件，随Case标注保存，页面没有独立排除裁决按钮。

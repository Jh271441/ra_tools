# Review 保存与筛选队列

## 约定

- 保存成功后重新读取当前筛选队列。当前 Issue 仍满足筛选时留在原条；已移出筛选时跳到原来的下一条，没有下一条则回到上一条；结果为空则回到 Gallery。
- Review 的完整 Issue 裁决沿用同一核对入口，覆盖 `label_state=conflict`；先刷新队列，再按需刷新仍选中 Issue 的详情和联合上下文。裁决仍为独立 Issue 写入，不创建模型 Review，也不完成个人标注任务。参见`review-issue-decisions.md`中的cache780生产修复。
- cache782将队列核对置于图库前：一次完整ID查询确定成员和顺序，先打开相邻详情，后台用本页ID补齐图库；缺项时回退完整新查询。临时队列支撑正确序号和连续保存，受账号/筛选/条数约束，图库提交后退休。后台图库失败不撤销已成功跳转。
- 联合任务选择“待完成”时，后端确认标签与模型复核均已提交才移出队列。前端不得仅凭一次点击或本地表单状态修改任务完成条件。
- 保存保留任务、负责人、Run、baseline、其他筛选、每页条数和滚动位置；跳转使用替换当前历史记录，URL 中页码对应新条目所在页。
- 直接 Issue 链接可以没有匹配的列表页。此时在提交前通过现有 issue-ids 查询恢复队列位置；如果当前条已被协作刷新移出待完成队列，则从同一任务顺序中定位相邻的剩余结果。
- 原最后一页仅剩当前条时，保存后正确回到上一页最后一条。列表中不再出现某条，也可能只是页边界移动，因此通过完整筛选 ID 队列核实成员关系后再跳转。
- 保存后的读取使用独立请求，避免复用保存前尚未结束的 GET；旧列表响应仍受请求序号与页面上下文保护。
- 图片后台保存沿用同一队列核对。只有仍在原页面、原 Issue、原任务/Run/负责人/筛选且没有新草稿或图片时才能自动跳转；用户已经切换上下文时不得被旧保存带回。
- 保存后的联合上下文读取失败不改变写入成功事实，也不阻止独立的队列核对。队列读取失败保留已保存状态、标记队列待刷新并显示既有中英文提示，不重新提交。
- Enter 成功后的说明框失焦会触发原生 change；应先释放焦点再清理已提交草稿，避免把刚保存的值误记为新编辑。真正发生在请求期间的新编辑继续保留且不自动跳转。
- 带图后台提交和普通提交共用草稿退休逻辑：服务器确认成功后，先消化原生失焦 change 并清理已提交字段标记，再核对队列。输入法仍在组合输入时保留焦点和草稿，不自动跳转。
- 自动跳转只等待提交确认和最新筛选队列，不等待旧 Issue 的联合上下文 GET。只有核对后仍停留在同一 Issue 时，才独立刷新其上下文和并发校验凭据；保存后的读取绕过上传前的在途 GET 合并，仍保留原有超时和重试；读取失败不能触发已成功上传的重试。

## 修改时保留 Case 图片

- 联合复核和不带 Run 的 Case 提交，创建新修订时继承当前账号在同一 Issue 的精确上一修订图片，再追加本次新图。并发版本和共享标签指纹仍须先通过校验；不继承其他账号、其他 Issue 或任意共享来源的图片。
- 每个修订有独立图片元数据和不透明 ID，复用原始不可变文件；历史版本不修改。已有图片加新增图片最多4张、合计24 MiB，前端提前校验，后端在同一事务里校验，超限回滚整个联合提交。
- 存储配额按文件实际引用去重计数；评论目录与 Review/Case/裁决目录分开计算。仅修改文字不会重复占用图片文件容量。无需数据库迁移，不批量重写已有历史修订。

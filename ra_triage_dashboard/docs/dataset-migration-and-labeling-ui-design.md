## 1. 本轮确定的用途映射

用户已明确：0522、0626、0821 的现有工作主要是标注，Review 说明也主要是标注依据；0206、0508 的历史批次包含模型判错复核。

按这一业务事实制定迁移默认规则，不再把所有 Review note 都当作无法归类的混合文本。

| 数据集 | 新页面默认入口 | annotation 默认用途 | note 默认用途 | 例外处理 |
|---|---|---|---|---|
| 0522 | Case 标注 | 标注版本 | 标注依据 | 明确的模型复核批次/记录可以配置覆盖 |

| 0508 | 模型复核/历史复核 | 保持历史复核语义，按批次核对 | 默认历史模型复核说明 | 同上；保留数据集原有用途约束 |

“主要/几乎都是”作为数据集默认规则，允许少量具体例外。映射优先级是：

```text
显式记录例外 > 明确任务批次规则 > 数据集默认规则 > 历史兼容待归类
```

不能通过“绑定了 Run”“填写过 missing_evidence”或 note 中出现“模型”几个字，自动否定用户给定的用途。自动扫描可列出待查看的样本，不执行语义猜测或改写正文。

0522/0626/0821 以后也可以做模型复核，0206/0508 以后也可以创建标注任务。这一映射定义现有历史数据与默认入口，不把数据集永远锁死成某种类型。

## 3. 数据集迁移：保持身份，变更用途和入口

### 3.1 五个数据集原样保留

保留以下逻辑身份和全量成员，不另建一套重复 Case：

| dataset ID | baseline scope | 迁移时注册数预期 |
|---|---|---:|
| 0206 | `release0206_1326_20260729` | 1326 |
| 0508 | `release0508_1071_20260729` | 1071 |
| 0522 | `release0522_100_20260908` | 100 |
| 0626 | `release0626_300_spotcheck` | 300 |
| 0821 | `release0821_1242_20260908` | 1242 |

迁移内容是“成员清单、工作集/任务、人工记录用途、来源映射和 UI 默认入口”。原 Issue ID、Trail 链接、基线成员身份、Run/预测、已有 GT、媒体索引和视频文件保留。

需要增加独立的数据集成员快照作为校验依据。不能只依赖某时刻可变的 `issues.baseline_scope` 字段重新归属历史：优先用注册数据集的冻结成员清单，若不同来源冲突则列入例外。

### 3.2 每个标注集的组织方式

每个数据集提供一个全量标注浏览范围，并在其中呈现已有任务或历史标注集合：

```text
0821（1242 个 Case）
  全量浏览：含未分配/没有工作台提交的 Case
  历史任务 A：抽样 200
  历史任务 B：低置信度追加 150
  历史任务 C：第三批 150
  任务外历史补充：保留 2 条原版本的来源
```

全量浏览是一个固定成员范围，不伪造一个“已经分配给所有人”的新任务。

0522、0626 当前没有 live 分配任务，先迁入“历史标注”集合，不补造人员、分配时间或完成率。确需重新分配时再基于完整数据集或已有子集创建新任务。

没有 Split 的历史标注按原来源 Run/来源批次保留上下文。已确认原 Run 是选样集合时，可以保存 Run 输出与数据集的交集为“来源覆盖工作集”；它不是原来的人工分配范围。无法证明曾分配的 Case 不进入历史任务应交数。

### 3.3 任务恢复流程

1. 读取 Split 的不可变创建快照、成员列表/顺序、reviewers_per_issue、交叉比例和筛选来源。
2. 用 `assignees_json[*].items` 或 `issue_ids` 恢复最初 Case 集合与人员槽位，校验保存的总数。
3. 按有记录的转派事件重建人员变化；现存 `review_work_assignments` 作为当前态核对，不作为唯一历史来源。
4. 保存 `legacy_split_id → task_id`，将原 Run 移到 `selection_source_run_id`，绑定恢复的 Workset。
5. 保留被后续任务覆盖的历史成员；历史槽位标为 superseded/archive，不重新激活，原历史提交仍可查看。
6. 任一快照无法恢复时停止该批次激活，列出缺口；不得执行原 filter_json 的当前查询凑出同样数量。

对于 0821 的三个批次，建议保留用户熟悉的 200/150/150 批次名称、Case 顺序、人员和交叉配置，只改变页面入口和业务类型。

## 4. 每类数据的迁移规则

### 4.1 annotations

对 0522、0626、0821 的每个旧版本建立一条标注版本映射：

| 旧字段 | 新位置 | 规则 |
|---|---|---|
| `id` | `source_annotation_id` | 唯一来源键；原记录保留 |
| `issue_id` | 同一 Case | 不生成第二个 Issue |
| `model_run_id` | 来源元数据/历史批次 | 不再作为标签只供该模型使用的限制；仍保留原值与来源 Run hash |
| `work_split_id` | `task_id` 映射 | 非空保持原任务；空值按历史自由标注处理 |
| `label/expected_output` | `expected_output` | 原值有效则保留；空值可用原 Tags+固定目录版本推导，明确标注来源 |
| `tags` | `case_tags` | 保留所有 keys 和历史目录含义，无法映射的保留 legacy key |
| `note` | `label_rationale` | 按用户确认用途原样迁移，不概括、不改写；明确例外走覆盖规则 |
| `missing_evidence` | `label_evidence_gaps`/历史证据项 | 保留 keys 和显示文案，不误记为模型原因统计 |
| `is_excluded` | 标签记录中的排除提议 | 保留 true/false 和作者版本；不自动执行 Trail 排除 |
| author/source/verified | 相同原始身份 | 不把历史未验证身份提升为 SSO 已验证 |
| `created_at` | `authored_at` | 迁移时间另外记；不重新排列作者原始时间 |
| `supersedes_id` | 原始链映射 | 尽可能映射同域来源；跨域/跨作者边保留 legacy 关系，不伪造新作者的覆盖权 |

状态重建必须分别得到：有历史提交、有效标签、任务已交人数、结果是否一致、与当前 GT 的关系。迁移不会生成任何过去不存在的 adjudication。

如果 Tags 能推导 label，记录固定的推导版本和 source=`tags`；若冲突则保留为空并标记需补充。当前 GT 只参与对照，不参与“补齐人工提交”。

### 4.2 latest/head 与结果重建

- 旧明确 Split：保留每个任务、Case、作者的版本链，重建该作者当前 head，再计算任务结果。
- 旧普通共享流：保留原来有效的共享 head 与接替链。不能把曾被另一个人替代的历史版本重新拿出来做独立投票。
- 相同 Issue/作者在不同历史 Run 或批次下的记录：全部保留各自上下文；不因新的标注不绑定评测 Run 而自动合并。
- 同一 Case 多任务结果相同：可以展示一致来源，但只在明确的结果集合中去重统计；各任务提交保持独立。
- 结果相互矛盾：显示跨来源待处理，后续显式裁决；不按迁移顺序、时间戳或最大源 ID 选择。

### 4.3 Review 说明与讨论评论分开迁

`annotations.note` 是跟随版本的说明，0522/0626/0821 默认成为标注依据。

`review_comments.body` 是独立的讨论消息。0821 的 49 条消息整体迁为标注讨论，但仍是讨论，不能从消息自动抽取标签或伪造标注提交。

讨论迁移保留作者、时间、Markdown、mentions、reply_to、附件及原 comment ID 映射。完整回复树作为一个整体迁移。旧讨论只有 Issue+Run 而没有 Split：

- 可以证明归属唯一任务时，以关联方式展示在该任务讨论中；原线程来源仍保留。
- 对应多个任务或不确定时，展示为 Case 的“历史标注讨论”，标明原来源，不强行归入某个任务。
- 不把不同 Run 的多个历史线程拼接成一个回复树，也不把同一消息复制成多个独立已发送消息。

旧 DChat/分享链接带 comment ID 时，通过映射定位新页面和原消息。迁移记录 outbox 已有状态但不重新派发通知；迁移 API 不调用普通新建消息的通知副作用。

### 4.4 截图、视频及外部参考

- annotation/comment 附件保留文件、checksum、MIME、尺寸和原所有者记录，新增新域关联；同一文件可以被历史和新页面引用。
- 新标签表删除或撤回不能直接级联删除仍被原 Review/讨论/裁决引用的证据。
- BEV、Camera、视频继续从同一个 media provider 和受限根目录读取。无需复制几千个 Case 的媒体目录。
- 视频布局、t0、快捷键、Ares/Event/录屏入口尽量原样复用；不会为了数据分类重新生成素材。
- 0626 的历史抽检 Excel/Tag 提示保持“来源资料”。没有真实保存动作或可信原始标注人信息时，不冒充工作台 author 提交；可以作为 imported evidence 提示。

### 4.5 GT 与模型数据

- Dataset membership、GT 和 Model Run 三类数据分别对账。
- 保存迁移时当前 GT 的不可变起始快照，标明来源与时间；不声称它是每条旧 Review 当时看到的 GT。
- 正式 GT 标签不因 note 被划归标注而改变，也不因为有 1242 个 Case 就给 0821 的 28 个缺 GT 成员自动补标签。
- 原有 Model Runs、predictions、导入源与 hashes 保留在模型区域，用于选样追溯和以后评测。
- 标注区域不展示模型结果；这不要求删除或改写该数据集的推理结果。

## 5. 迁移工具与流程

已实现服务端离线迁移工具，按迁移批次和数据集运行，阶段与业务 deploy 分离。命令默认仅盘点；`backfill` 和 `activate` 必须显式传入 `--apply`：

```text
python3 ra_triage_dashboard/scripts/migrate_case_labeling.py plan \
  --datasets 0522,0626,0821 --policy-version <versioned-policy>
python3 ra_triage_dashboard/scripts/migrate_case_labeling.py backfill \
  --datasets 0522,0626,0821 --policy-version <versioned-policy> --apply
python3 ra_triage_dashboard/scripts/migrate_case_labeling.py reconcile \
  --datasets 0522,0626,0821 --policy-version <versioned-policy>
python3 ra_triage_dashboard/scripts/migrate_case_labeling.py activate \
  --datasets 0522 --policy-version <versioned-policy> \
  --expected-epoch <n> --actor <ldap> --apply
```

工具只在云端运行，不把生产数据库、备注正文或媒体打包拷到 Mac。开发侧保留脱敏统计、规则与测试 fixture。

### M0：映射清单

生成版本化 migration manifest：数据集与 membership hash、源 schema/代码版本、任务映射、annotation 分类规则、记录/线程级例外、GT 起始快照引用、各表计数和源内容 hashes。

有优先级的声明式 policy 至少包含：

```text
dataset_defaults: 0522/0626/0821 → labeling
task_overrides:   已明确的历史复核或纯标注任务
record_overrides: 少量已确认例外，不使用文本分类猜测
thread_routes:    唯一任务/Case 历史讨论/旧模型讨论
unassigned_policy: 保留历史集合，不造任务槽位
```

已完成的是本次汇总盘点。逐记录映射、例外清单和正式 snapshot manifest 留给实施阶段生成。

### M1：准备增量 schema 和兼容版本

先发布同时能读取旧数据与新数据的兼容版本，准备新表、来源映射、结果引用、附件关联、路由映射以及每个迁移范围的 schema/cutover epoch。

新记录先处于影子范围，不改默认页面和生产统计。数据库 migration 需要经过备份/恢复校验和发布门禁，不能在应用启动时偷偷执行全量回填。

### M2：恢复库试迁移

在云端可控的隔离数据库中恢复逻辑备份，媒体只读复用，禁用所有外部写入、推理任务和通知发送。对恢复库运行同一组 `backfill` 和 `reconcile` 命令；生产 backfill 前必须保存其通过报告。

`scripts/rehearse_case_labeling.py` 提供这一演练入口，必须使用干净的已提交 checkout、云端备份 checksum 和同用户 0600 的发布运行配置：

```text
python3 ra_triage_dashboard/scripts/rehearse_case_labeling.py \
  --backup <cloud-postgres-backup.dump> \
  --runtime-config <release>/production-env.json \
  --datasets 0522
```

工具生成专用临时 PostgreSQL 库，始终覆盖目标 DSN，连续执行两轮回填/对账，随后在该一次性库内对每个演练数据集执行 `activate` 切换（M6 原子 epoch/指纹校验 + 激活后复核），核验切换后原始 GT、Review、模型数据、人员分配及通知表的内容 hash 仍不变，并只读检查附件文件大小和 SHA-256。激活只发生在临时库；生产执行激活仍必须另行走 M5/M6 门禁。演练结束后删除临时库。完整报告仅保存于云端 `ra_triage_dashboard_deploy/labeling-rehearsals/`，本地记录非敏感汇总即可。清理失败仍保存失败报告及准确的临时库名。

M6 的代码部分已于 2026-09-18 补齐并纳入演练：`activate` 在同一事务内行锁下重算源清单指纹、校验 expected-epoch 后才切换 active；激活后立即复核，若切换窗口内出现源写入则自动把该范围置为 paused 并终止。旧写入口交接：数据集激活后，旧 Review 的标注保存、附件批量保存、版本删除和讨论评论创建接口对该范围返回 409 并指向 Case 标注工作台。仍需注意：标注页面当前没有讨论写入入口，0821 激活前必须先在标注页提供任务/Case 讨论；跨进程的写入屏障由“激活后复核 + 自动暂停”兜底，服务级短暂屏障属于生产切换时的运维步骤。

按以下次序建立映射：

1. 数据集成员与当前 GT 起始快照。
2. Worksets、任务定义、原始/当前人员分配及转派历史。
3. 标签 Case 与 annotation 所有版本，再连接版本链和 heads。
4. 评论线程、消息、回复、附件和历史链接。
5. 标注结果、有效性/冲突状态和新读取投影。

脚本可以重复运行，按 `(source_table, source_id, target_domain, policy_version)` 去重。更正 policy 时生成新映射版本，旧映射变为被替代状态；不在统计中并列激活两次。

### M3：逐数据集对账

至少生成四份报告：

- `dataset-reconciliation`：全量成员、GT、媒体与 Run 引用。
- `record-reconciliation`：人工版本、正文 hashes、身份、附件、回复/版本链。
- `task_reconciliation`：每个任务的原始范围、现存槽位、历史槽位及有效提交。
- `projection-differences`：旧页/新页的统计与状态差异，并给出分类理由。

“任务完成度更准确”“普通 label 与 GT 相同不再算模型归因完成”等预期变化单列。任何无法解释的丢失、重复或来源变更都不能以“新口径”概括过去。

### M4：生产影子回填与差量核对

在应用继续服务时读取一致性只读快照，回填新表但不激活。当前约千级历史版本，优先采用有上限的全量 hash 重扫与差异修正，暂不引入复杂 CDC 系统。

差量检测必须覆盖新增、原记录删除、supersedes 改写、附件变化、人员转派、数据集映射和 GT 同步。仅记录 `max(annotation.id)` 无法发现删除和重写，不能作为唯一进度点。

生产 backfill 有明确批次/策略版本、限流、失败重试和断点；不向 notifications/outbox 新增事件，也不产生 Trail 操作。

### M5：确定逐数据集激活顺序

激活命令每次只接受一个数据集，且要求 reconcile 通过及精确 `expected-epoch`。激活顺序建议：0522 → 0626 → 0821 → 0206/0508 的已确认批次。

- 0522：验证已有 GT 与工作台历史标注分离、无 Split 记录、截图和页面路由。
- 0626：验证同 Case 多版本、不同来源 Run、历史 Excel 提示与真实提交区分。
- 0821：验证三个任务、交叉比例、缺 GT、937 条 Split 版本、2 条普通补充、49 条讨论和冲突裁决。
- 0206/0508：保留旧模型复核工作区，先按批次生成分类清单，确认能安全归类的再切换；待归类记录继续可访问。

0522 的样本不足以证明多人并发正确。0821 激活前必须已经通过隔离库的真实多任务数据核验和独立并发测试。

### M6：最终写入交接

每次按单个数据集/任务范围切换：

1. 兼容服务启用该范围的短暂写入屏障，提示维护并保留客户端草稿。
2. 等待已进入事务的写入结束；相关 GT 同步、删除、跨范围分配等会改动源对象的操作也纳入屏障。
3. 最后一次重扫差量、同步删除/改链与分配变更，重新校验 hashes 和计数。
4. 原子切换范围 epoch、读路径、新写入入口和路由映射。
5. 解除屏障，验证首个新保存、附件、历史、列表、统计和导出。

旧标签页和后台附件队列提交必须携带上下文/epoch，服务端拒绝过期上下文并提示刷新；不允许切换后旧接口仍静默写旧表。客户端保留草稿和上传文件供重新确认范围后重试。

写入屏障时长由试迁移测量，目标只覆盖最后差量和切换；不提前承诺几秒内完成。共享 Run 删除等跨数据集操作若触及迁移范围，应在这段窗口阻止该操作，不能漏过屏障。

### M7：观察与回退

观察真实标注保存、页面切换、草稿、附件、GT 候选和任务进度，使用源映射核对。

新界面有问题时回退到能读取新数据的兼容页面，必要时暂时关闭该范围写入。已有新提交继续保留。不能在新提交存在后直接切回仅认识旧 annotations 的版本，再声称迁移已经完整回滚。

旧表、旧附件和映射表在稳定观察期保留。清理属于后续单独任务；不会因标注区上线自动删除原 Review、Model Runs 或媒体。

## 6. 必须通过的对账条件

| 层级 | 通过条件 |
|---|---|
| Dataset | 成员 ID 集合及 hash 完全一致；无 GT 的 Case 仍在，未标注 Case 仍在 |
| GT | 起始快照与同一源快照逐 Issue 对应；迁移不改 GT 值 |
| Annotation | 每个源版本有一个明确主归属或明确保留的 legacy 归属；无丢失/重复生效 |
| Note | 0522/0626/0821 默认迁为标注依据，正文 bytes/hash 不变；例外有 policy 记录 |
| 身份与时间 | 原 author、verified、source、authored_at 不变；migrated_at 单独记录 |
| 版本链 | 全部源边有对应的映射或有理由的 legacy 引用；不制造循环或跨作者投票 |
| Task | Case 集合、人数、交叉比例、顺序和转派事件可对应；被覆盖历史槽位不复活 |
| Comment | 每条消息一次、回复关系完整、源线程可定位；不制造新标注或新通知 |
| Attachment | 数量、hash、MIME、大小和可读取性对应；共享引用不复制计数或误删 |
| Prediction | 原 Run ID、预测数量/hash 不变；标注 API 不返回预测字段 |
| 统计 | GT 覆盖、人工覆盖、任务进度分别对应；预期差异逐类解释 |
| 导出 | 标签明细可以完整回溯；GT 更新表不含未解决冲突/缺交/过期结果 |
| 并发 | 写屏障前后都无丢写、双写；重复请求幂等，旧 epoch 写入被拒绝 |

试迁移对当前只读盘点的预期是：三个新标注集有 1642 个 Case，1024 条 annotation 源版本，49 条讨论消息和 23 个 annotation 附件。正式执行时用最终一致性快照替换这些时点数字。

## 7. UI：两个独立工作区，复用同一套组件

### 7.1 独立路由与状态

建议新增 `/case-labeling`（RA Case 标注），保留 `/review`（模型复核）。现有 `/intent-labeling` 是另一业务，不复用这个名称或路由。

两个页面各有独立的顶层控制器、筛选状态、数据请求与保存动作；共享基础组件。标注页不会因为用户上一页选过 Run 而加载/绑定模型输出。

| 标注工作区 | 模型复核工作区 |
|---|---|
| 数据集、任务、标注状态、人员、Issue 筛选 | 数据集、Run、复核任务、模型对照和人员筛选 |
| Case 媒体与事实信息 | 相同 Case 媒体与事实信息 |
| 期望输出、Issue Tags、标注依据、证据缺口、截图 | 模型预测、confidence、Reason、模型诊断、缺失信息、截图 |
| 标注历史、任务讨论、冲突裁决 | Run 复核历史、讨论、GT 待复核入口 |
| 标注覆盖与任务交付、标注/GT 候选导出 | 模型原因覆盖与聚类、诊断导出 |
| 主按钮：保存标注 | 主按钮：保存模型复核 |

标注工作区不显示模型结果、判错原因区域、MISMATCH/MATCH 筛选、模型对照 badge、API 推理操作、Run 预测历史或模型 Reason。任务详情的来源说明仍可展示“从某次推理选出的低置信度子集”，不展示该 Case 的预测值。

数据集已有 GT 覆盖可作为管理信息显示；初标表单不主动展示 GT 对照，GT 核对/裁决流程按需要提供参考。标注页面的媒体只保留任务允许的事实证据，默认不打开模型历史快捷键。

### 7.2 组件复用，不复制整个页面

| 可复用组件/能力 | 输入应是什么 | 页面决定的业务 |
|---|---|---|
| 数据集选择、Issue 查询、分页/队列 | 明确的 scope 与查询结果 | 标注/模型筛选条件 |
| 媒体播放器、BEV/Camera、t0、放大、布局 | Issue 与 media descriptor | 是否提供模型工具条 |
| Issue 标签与期望输出编辑器 | 标签目录、当前值、可编辑状态 | 属于 label revision 还是历史只读引用 |
| 文本/Markdown 编辑器、@mention | 文本、字段名、当前记录上下文 | 标注依据、模型原因或讨论正文 |
| 附件选择、粘贴、拖放、上传/重试 | 明确 record owner、草稿 key、submit callback | 发往哪个域接口 |
| 历史版本列表、对照、身份和时间 | 规范化的版本条目 | 哪些字段可见、是否能撤回/裁决 |
| 讨论面板 | thread scope 与消息列表 | 标注任务/Case 讨论或模型复核讨论 |
| 分配/转派/人员进度 | 任务类型与统计 payload | 标注任务或模型复核任务 |

复用表示保留一份组件实现和样式；不同页面按业务需要组合，并不要求标注页包含模型专用组件。

现有前端是 classic-script modules 和共享 state，第一步应把组件依赖从 `state.selectedRunId / state.selectedCase` 等全局变量，逐步改成显式 context：

```text
workspace = labeling | model_review
dataset_scope, task_id, case_id, author
label_case_id（标注）
evaluation_run_id, reference_snapshot_id（模型复核）
```

基础组件通过 callbacks 读写业务记录，页面控制器拥有上下文。继续使用现有 MANIFEST/loader 和样式，不为此次迁移引入整套新前端框架。

### 7.3 服务端 payload 分离

当前 `database.get_case()` 默认返回 annotations、所有 predictions、推理 jobs、batch jobs。新的标注页面不直接沿用这个完整 payload，再用 CSS 隐藏一半。

提供专用 labeling detail/summary 查询，只返回 Case 事实、媒体描述、label revisions/results、允许的讨论、任务上下文与所需 GT 参考。模型专用数据从模型复核接口读取。

这同时减少标注页请求量，并保证换路由、缓存或刷新不会把模型 UI 带入。历史标注依据本身如果提到了模型，按原始人工文本保留；这不等于向标注页注入模型预测组件。

### 7.4 深链接与草稿

- 有已迁移 task ID 的旧链接精确跳到该标注任务。
- 旧 `/review?issue=...&run=...` 若由 manifest 唯一映射为标注来源，则定位对应历史标注范围；不能证明唯一时保留兼容落地页，让来源可选，不自动挑最新任务。
- 真正模型复核的记录级例外保持在 `/review`。
- 评论深链接定位到同一源消息及其回复，迁移不重发 DChat。
- 新草稿包含 workspace/Task/Issue/author/必要的 Run 或 LabelCase；旧草稿恢复前显示目标，正文原样保留。
- 浏览器返回/前进恢复各自页面状态，标注区不继承模型复核的 Run/comparison 过滤。

## 8. 实施顺序与本轮评审点

推荐把总体路线细化为：

1. 映射政策与逐记录迁移清单；准备兼容服务和共享组件边界。
2. 独立标注页面、最小 label 数据结构、裁决/导出候选规则，完成 0522 隔离试迁移。
3. 激活 0522，迁移 0626，验证来源提示、说明和附件。
4. 完成 0821 三批任务、讨论、标签冲突和裁决的试迁移/核验，再整体切换这些明确范围。
5. 0206/0508 保持模型复核入口，逐批补全用途映射，最后处理确有混合字段的例外。
6. 统一跨任务统计与跨 Run 参考版本，收尾历史兼容。

本轮建议采用的默认项已落实在设计中：三个新数据集以标注用途迁移，note 默认是标注依据；旧数据集按批次处理；标注/模型复核是两个独立页面，组件与样式复用；迁移通过来源映射可重复核验；现有正式 GT、模型输出和媒体保持各自身份。

截至 2026-09-18，独立标注页、基础数据结构、writer 裁决、来源受控 GT 导出、历史 annotation/comment/附件映射和迁移脚本已实现并通过本地数据库/前端契约测试；M6 的事务内 epoch/指纹原子激活、激活后自动复核暂停与旧写入口 409 交接已补齐。0522 的恢复库演练（含两轮回填/对账与激活切换）已通过；0522/0626/0821 尚未在生产执行 backfill 或激活；0206/0508 未迁。现有模型复核写入和原因分析保持原路径，等待后续 P3 的专门迁移与影子对照。

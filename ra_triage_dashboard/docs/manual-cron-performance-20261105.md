# 每日任务冷快照性能优化（2026-11-05）

## 6.5 秒代表什么

此前 6.51 秒来自 `/api/daily-cron` 在进程重启后的一次快照重算，包含服务端读取和传输，
并非页面静态资源下载时间，也不是稳定的 p95。接口有 5 秒 single-flight 缓存，
缓存命中通常只有十几毫秒；缓存失效仍需要完整核对监控数据、历史耗时回执、媒体和版本状态。

本次对同一线上版本 `9157e997` 重新测量，三个真正重建的 HTTP 请求为
2365.4 / 2267.1 / 2165.0ms，中位数 **2267.1ms**；紧随其后的热请求中位数 **11.4ms**。
通过 `observed_at` 确认重建发生在请求期间；两轮之间等待超过 5 秒。
这是服务端 loopback 的接口测量，不含公网、SSO 和浏览器渲染。

## 定位与修改

一次没有 profiler 的完整重算约 2057ms，其中监控 GET 最慢约 438ms、
主流程耗时回执约 407ms、历史媒体约 194ms、版本状态约 1016ms。
原实现先等待三个监控请求，再依次执行本地投影。

- 三个固定监控 GET 保持最多 3 个并发；等待期间执行本地投影，重叠网络和本地读取。
- 大量文件扫描并发实测更慢，最终保留本地单线程扫描，不增加文件扫描线程池。
- 历史日和按版本投影共享一次 `CloseupCohort`，队列由每次快照读取 2 次变为 1 次。
- 同一 Issue/Scope 的近景核验结果在本次快照内复用，最多 4000 项，包含不存在的回执。
- 计数仍通过原 `_load` 完整核对回执、配方、范围、视频和封面文件；只复制计数实际需要的 trip、anchor 和 producer，避免反复深拷贝完整回执。
- 规划文本按版本及汇总共享一次有界只读索引读取，实测由 5 次降为 1 次；每个范围仍按精确 Issue/Trip/Anchor 单独计算。
- 主流程耗时读取每次解析一次可信根目录；每份回执、attempt 的路径及软链接检查继续执行。

5 秒缓存有效期、30 秒页面刷新、只读连接、数量/大小/耗时上限、缺失和不可用状态保持既有契约。
本次没有增加持久快照、缓存有效期或后台采集任务。
